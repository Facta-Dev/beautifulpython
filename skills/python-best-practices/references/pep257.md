# PEP 257 (digest)

Source: [PEP 257 — Docstring Conventions](https://peps.python.org/pep-0257/).
The conventions every docstring-aware tool (`sphinx`, `pdoc`, doctest) builds on.
License: public domain (PSF PEP license).

## What a docstring is

The first statement of a module, class, or function body is its docstring — kept in
`__doc__`, surfaced by `help()`, Sphinx, IDEs, and the API browser. Conventions here
exist so tools can parse and present them predictably.

## The one-line rule

One-line docstrings fit on one **physical** line: the closing quotes are on the same
line as the opening quotes, and the whole thing fits in the line-length limit.

```python
def kos_root():
    """Return the pathname of the KOS root directory."""
```

Rules for one-liners:

- Triple double-quotes even for one line (expansion stays cheap).
- No blank line before or after.
- Imperative mood: """Return ...""" not """Returns ...""" (the docstring describes the
  contract, not the narrator).
- Don't restate the signature in prose.

## The multi-line rule

Multi-line docstrings: a one-line summary ending in a period, a blank line, then the
detail. The summary line is what listings, tooltips, and index pages show — budget it
like a title.

```python
def complex(real=0.0, imag=0.0):
    """Form a complex number.

    Keyword arguments:
    real -- the real part (default 0.0)
    imag -- the imaginary part (default 0.0)
    """
```

- Blank line after the summary, before the detail. Tools use it to split.
- Closing quotes on their own line.
- Indent the docstring body to the level of the code it documents.
- The blank line between summary and detail is **not** required for one-liners.

## DRY: don't describe the interface twice

The signature already carries parameter names, types, and defaults. The docstring adds
what the signature cannot say:

- What the function does at the level of intent.
- What it raises and when.
- Side effects (mutates its argument, writes a file, changes global state).
- Pre- and post-conditions.
- Performance characteristics when they're a contract ("O(n) in the number of items").

Don't write `"""This function is add_item and it takes a name and a qty and returns
nothing."""` — that is a worse version of the signature.

## Where each docstring goes

- **Modules:** at the top, after the shebang and module-level comments. Mention what
  the module exports and who should use it, not the history of the file.
- **Classes:** below `class`, before the first method (attribute docstrings work too).
- **Functions/methods:** required for public ones; private helpers get them when the
  name doesn't tell the whole story.
- **Scripts** and interactive-only modules: docstring also usable as a usage message
  (`python -m "module" --help` reads `__doc__`).
- `__init__` docstring vs class docstring: pick one place for the constructor contract
  (usually the class), not both with different words.

## Semantics sections for exceptions and returns

PEP 257 predates the section conventions (Google, NumPy), but the semantic rule stands:
a docstring **must** note a function that raises (which exceptions, under what
conditions) and a function whose return value isn't obvious. Callers write `try/except`
against your docstring, not against your source.

## Style notes the PEP settles

- """Quotes""" everywhere — not `'''` (apostrophes inside stay simple).
- No blank line immediately after the opening quotes in a multi-line docstring.
- Doctests (`>>>`) inside docstrings are fine and executable; they count as
  documentation first and tests second — keep them correct or remove them.
- Preserve whitespace inside the docstring for examples that need it.
- No de-facto standard exists for section headers; PEP 257 defers to the project. The
  Google style (`Args:`, `Returns:`, `Raises:`) is the common modern choice; NumPy style
  is common in scientific code. One project, one style, enforced in review.
